# Design: add-test-gap-analysis

**Approved at Gate 2 (2026-11-14):** Ervin approved this design as
written.

## Context

See proposal.md for why; the specs `test-analysis` and `configuration`
for what. What the design has to work with:

- **The model.** `qgate-lang` gives each file a `FileModel`: function
  units (qualified name, line, cyclomatic complexity), imports, usings
  and normalized tokens. A unit has no end line and nothing that tells
  whether its code changed. The normalized tokens cannot tell either:
  they map identifiers to `$id` and literals to `$lit`, so
  `return a + 1` and `return a + 2` look the same.
- **Analyzers never see source text or the file system.** The
  per-file `Analyzer` trait receives one `FileChange`. Duplication,
  which needs the whole change and every head file, is a separate
  repository-level analysis the CLI feeds.
- **What the CLI already has in revision mode** (`check_revisions`):
  - `Changes { changed, deleted }` from git, with renames, before any
    selection;
  - the `FileSelection` (supported, not excluded, not generated by
    name);
  - the analyzed `FileChange`s;
  - inside `duplication()`, the head file list from `files_at`.
- **Configuration.** `qgate-config` turns `qgate.toml` into plain
  strings (ADR 0003). The analyzers' `PathPatterns` interprets path
  patterns and is already shared by architecture rules and
  `[files] exclude`.

## Goals / Non-Goals

**Goals:**

- Findings that come from paths and models alone, with no extra file
  reads beyond the head file list duplication already reads.
- The pairing conventions live in one place, so the evaluation can
  adjust them without touching the CLI.

**Non-Goals:**

- Reading `.csproj` contents or `package.json` contents. Only their
  paths matter (but see D3 for a fallback).
- An `Analyzer` trait change, or a common "repository-level analyzer"
  abstraction. Two such analyses do not yet justify one.

## Decisions

### D1. Each unit gets a fingerprint of its code (Gate 1, question 2)

`Function` gets a `fingerprint: u64`, a hash of the unit's own code.
The code is the text of every leaf token that the unit's complexity
walk visits, so it excludes:

- comments;
- whitespace (tokens are hashed with a separator, not with the
  layout between them);
- nested named units, which have their own fingerprint.

Nested anonymous functions are part of the unit, as for complexity.
Semicolons are left out too, as for the normalized tokens, so adding
or dropping them in TypeScript is layout.

**TypeScript types are not code here (decided during PR 1,
2026-11-14).** Task 1.1 asked for a changed type annotation to change
the fingerprint; this section and the proposal ("type-only edits ...
need no test") said the opposite. Ervin chose to leave types out. The
TypeScript walk does not enter type-level subtrees, so a unit whose
only edit is a type annotation is unchanged, as its normalized tokens
are. In C#, types are code and keep counting, as for duplication.
Other formatter edits, such as trailing commas or parentheses around
an arrow function's single parameter, still count as changes.

**C# directives are code (decided during PR 1).** The lines of
conditional compilation inside a unit (`#if DEBUG`, `#else`) count,
because changing them changes what compiles. `#region` and
`#endregion` lines are left out like comments: they only label code.
(A first version hashed them; the review of PR 1 found that it made
whitespace in a region name a change.)

**Code around a unit that belongs to it (review of PR 1).**
- *A bound call:* in `export const GET = withAuth(async () => ...)`
  the unit is the binding, so the call's own code counts. Swapping
  `withAuth` for `withAdmin`, or changing its options or a `debounce`
  delay, changes `GET`.
- *Method decorators:* the TypeScript grammar puts them before the
  method in the class body, so the walk would leave them out. They are
  runtime code (Angular's `@HostListener`) and C# attributes already
  count, so the method's fingerprint scans them when its unit opens.
  Class and field decorators belong to no unit.
- *JSX text* counts by its words. JSX collapses the whitespace in text,
  so a reflow of a component is layout. (Whitespace within one line is
  kept by JSX, so `<p> a </p>` and `<p>a</p>` are taken as equal
  though they render differently; accepted.)

Both adapters (TypeScript/TSX and C#) compute it in the walk they
already do, so parsing is not repeated.

- **Hash:** `std::hash::DefaultHasher::new()`, which has fixed keys.
  Fingerprints are only compared within one run of one binary and
  never printed, so stability across Rust versions does not matter. A
  64-bit collision that hides a change is negligible.
- **Alternatives:**
  - an end line per unit, with the analyzer comparing the normalized
    tokens in that range: blind to changed literals and names;
  - the raw text per unit as a `String`: the same answer, at the cost
    of memory for every head file duplication parses;
  - file-level change detection: rejected at Gate 1, question 2 (b).
- **PR 1** carries only this, with adapter tests: same code with other
  layout or comments gives the same fingerprint, a changed literal or
  name a different one, and a nested named unit's change leaves its
  parent's fingerprint alone.

### D2. A whole-change analysis in `qgate_analyzers::tests`

The module the crate docs already announce, `tests`, gets one
function, pure and I/O-free, roughly:

```rust
pub fn analyze(input: &TestInput<'_>) -> Vec<Finding>
```

`TestInput` holds:

- the analyzed `FileChange`s;
- every path of the head revision;
- the paths the change added, edited or renamed (to their new path),
  taken from git's raw list before `FileSelection`;
- the `[tests] exclude` patterns as `PathPatterns`.

The rule ids are constants, as in complexity: `UNCHANGED_TEST_RULE`
and `MISSING_TEST_RULE`.

- **Why not an `Analyzer`:** a finding depends on other files of the
  change (the test) and on the head tree (whether a test or a test
  project exists). Duplication made the same choice.
- **Why raw changed paths:** test files count regardless of
  `[files] exclude` and of generation (Gate 1, question 6). The
  analyzed changes alone would miss an excluded spec.

### D3. Conventions from paths only

- **TypeScript:**
  - the test suffixes are `.spec` and `.test`, before any TypeScript
    extension: `.ts`, `.mts`, `.cts` or `.tsx`;
  - the stem is the file name without its last extension, so
    `cart.service.ts` has the stem `cart.service`;
  - a source's tests may have any of the four extensions, whatever its
    own, so `order.mts` is tested by `order.spec.ts` (aligned with D6
    in the review of PR 1).
- **C# projects:** an index built once from the `.csproj` paths in
  the head list:
  - it maps each directory with a project file to that project's name;
  - with two project files in one directory, the first by name wins;
  - a file's project is found by walking up its directories.

  Test projects are grouped by their name without the last segment:
  `Domain.UnitTests` belongs to `Domain`. A test file is found by file
  name in any directory below a test project's directory.
- **Fallback, if the evaluation needs it:** pair test projects by
  `<ProjectReference>` in their `.csproj`. That needs the CLI to read
  each test project's file and a small scan of its references. It
  would cover eShop's `Ordering.UnitTests`, which references
  `Ordering.Domain`. It is not in the plan. If question 1 or the
  evaluation calls for it, it is decided with Ervin before PR 2
  merges, and the spec changes with it.
- **Paths compare byte for byte, case-sensitively,** as git stores
  them. `OrderTests.cs` does not pair with `ordertests.cs`.

### D4. Which changed units, which file is "new"

- **Changed units:** match the head version's units against the base
  version's by qualified name, as complexity does. A unit is changed
  when it has no match, or its fingerprint differs.
- **"New file":** the base version had no units at all. That covers:
  - added files;
  - files renamed from another language family or out of an excluded
    path (their base model is empty, as for complexity);
  - files that get their first function.

  The analyzer needs no extra flag for this.

### D5. Scope of `tests/missing-test` (Gate 1, question 5)

- **TypeScript:** the "project root" is the nearest directory at or
  above the file with a `package.json` in the head list, else the
  repository root. It is in scope when any head path below it is a
  TypeScript test file.
- **C#:** the file's project has at least one test project (D3).

Both come from the head list, computed once per run.

- **Alternatives:**
  - no scope: every new TypeScript file in a repository without specs
    would warn;
  - "the same directory has a spec": misses a new feature folder,
    exactly the new code that matters most.

### D6. Findings

- **Location:** the source file's path, at the line of its first
  changed unit in source order. `end_line` and `related` stay empty;
  `related` needs lines, and a test that is expected to change has
  none to point at.
- **Messages:**
  - `<first> changed, but not its test <test>` for one changed unit;
  - `<first> and <k> more changed, but not its test <test>` for
    several;
  - `, and <m> more` after the test when there are several unchanged
    tests, the first named by path in byte order;
  - `<first> has no test: expected <dir>/<stem>.spec.<ext>`, with the
    source's own extension (`order.spec.mts` for `order.mts`), or `... have no test: ...` with
    `and <k> more`;
  - for C#, `expected <Stem>Tests.cs in <test project>`, naming the
    first test project by name.
- **Ordering** follows the CLI's existing sort; no new key.

### D7. `[tests] exclude`

- **Config:** `qgate-config` gets `Tests { exclude: Vec<String> }`
  with `deny_unknown_fields`, like `Files`.
- **CLI:** copies the list into `PathPatterns` and names
  `tests.exclude` in a pattern error, as it does for `files.exclude`.
- **Analyzer:** matches the patterns against the source file's head
  path only. Test paths are never exempted (exempting a test would
  mean nothing).

### D8. CLI wiring

- **Head list:** `check_revisions` reads the head file list once and
  passes it to both duplication and test analysis. Today
  `duplication()` reads it itself.
- **When it runs:** test analysis runs when `analyzed` is non-empty,
  as duplication does. Its findings join the others before the sort.
- **Other entry points:** `--worktree`, the Claude Code hook and the
  MCP server go through `check_revisions` and need no change of their
  own. End-to-end tests cover the CLI and one MCP call.

### D9. On by default (Gate 1, question 5)

No switch:

- `[tests] exclude = ["**"]` turns the analysis off;
- warnings do not fail by default.

The release notes of 0.7.0 name the two new rule ids and say that
`--fail-on warning` users may see new failures.

### D10. Evaluation and rehearsal (Gate 1, questions 7 and 8)

- **Evaluation, task 2.6, before the tag:**
  - **Repositories:**
    - `bitwarden/clients`;
    - `bitwarden/server`;
    - `jasontaylordev/CleanArchitecture`, with its Angular client;
    - once, `dotnet/eShop`.
  - **Run:** for each, `qgate check` over the last 30 commits that touch
    `.ts` or `.cs` code, with `[files] exclude` set for migrations and

  - **Record in this file:**
    - each finding, sorted by hand: *should have changed*,
      *refactor*, or *miss* (the commit changed this code's test under

    - the count of edited existing files without a test (question 3).
  - **Stop rule:** misses above a third of a repository's findings stop

- **Azure rehearsal, task 4.2:**
  - **Setup:** the README's Linux job at 0.7.0 in

  - **Expected:**
    - two Warning rows in the comment;
    - two warning build issues;
    - a passing check step.

## Review of PR 1

The reviewer found no blocker. Fixed:
- JSX text whitespace made a reflow a change; it now counts by words;
- a bound call's own code (the wrapper, its options) and TypeScript
  method decorators were left out of the unit; both count now, as C#
  attributes do;
- whitespace in a `#region` name was a change; region lines are now
  left out, and a test pins that a directive's condition counts;
- the proposal named only whitespace and comments as ignored;
- D3 and D6 disagreed on `.mts` sources; every TypeScript extension now
  works alike (spec "TypeScript tests", scenario "An ES module source");
- task 2.3 now lists the scenario "Only a TypeScript type annotation".

## Risks / Trade-offs

- **[A team's names differ from the conventions]** → a stream of
  wrong `unchanged-test` / `missing-test` warnings, or silence.
  Mitigation: the evaluation's stop rule, the expected test named in
  every message so a reviewer sees the assumption, `[tests] exclude`,
  and the D3 fallback ready if needed.
- **[Refactors rightly leave tests alone]** → warnings a reviewer
  dismisses. Mitigation: Warning only, one per file, never Error.
- **[Signature-only edits]** A C# parameter change renames the unit
  (`Total(int)` → `Total(long)`), so it counts as new and changed.
  That is intended: callers in tests usually need to follow.
- **[Partial classes and multi-class files]** `Order.Validation.cs`
  pairs with `Order.ValidationTests.cs`, which nobody writes. Accepted
  for 0.7.0. The evaluation counts it, and a later change can pair by
  class name.
- **[Upgrade with `--fail-on warning`]** → new failures. Mitigation:
  release notes, and `[tests] exclude = ["**"]`.
- **[Hook nudges mid-edit]** The Claude Code hook reports warnings
  while an agent has not yet written the test. That is the point of
  M3: the agent learns before the pull request. Accepted.
- **[Cost]** A fingerprint per unit and a pass over the head list.
  Both are linear and small next to parsing. The evaluation measures
  it.

## Migration Plan

Nothing to migrate: a new analyzer, a new optional table. Rolling back
means pinning 0.6.0.
