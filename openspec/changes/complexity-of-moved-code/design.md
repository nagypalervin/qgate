# Design: complexity-of-moved-code

## Context

`ComplexityAnalyzer` implements `Analyzer`: the CLI calls it once per
changed file with a `FileChange`, and it matches the file's before and
after units by qualified name (`complexity.rs`). It never sees another
file, nor a deleted one. The CLI already gathers what a cross-file view
needs:

- `analyzed`: every changed file's `FileChange`;
- `left`: the base blobs of supported files that are gone (deleted,
  generated by header, or renamed to another language or family).
  `duplication()` parses these, but keeps only their tokens.

`qgate-lang` gives every unit a qualified name, unique within the file;
a cyclomatic value; and a fingerprint of its own code (the code of nested
named units left out). It also gives every file its normalized tokens,
each with a line. Nothing yet links a token to its unit.

The evaluation (`evaluate-angular-dotnet`) found two cases:

- CL11, `decryptManyV2` inlined into `decryptMany` (4 -> 12, a false
  Error);
- SV19, `RunSuccessTestAsync(...)` moved from `IdentityServerSsoTests`
  to `SsoLoginTestHelpers` in another file (a new function of complexity
  12, noise).

Its 0.9.0 reports of the 150 pull requests are the baseline: 59
complexity findings, 10 of them Errors.

## Goals / Non-Goals

**Goals:**

- No finding for a function whose code only moved, within a file or
  across files, out of a deleted file too.
- No Error for a function that grew only by the code of a function the
  same change removed.
- Everything else reported as before. A pull request that also adds
  logic to the moved or inlined code is still reported, for the added
  part.

**Non-Goals:**

- Renames in place, signatures changed by a parameter (SV6), and a new
  function made of removed ones: they stay as today.
- Duplication (the second fix), and C# 14 `extension` members.

## Decisions

### D1. Complexity runs once per change and language family

`complexity::analyze(changes, gone)` takes the `FileChange`s of one
language family and the parsed base models of that family's gone files.
It returns the findings of all of them. The CLI calls it once per family
after the per-file loop, in the same way as it builds a duplication index
per family. `ComplexityAnalyzer` stays an `Analyzer`. Its `analyze` is
`complexity::analyze(&[change], &[])`, so the two-file form of `qgate
check` and the doc example keep working, and moves within that one file
are covered too.

The CLI parses each gone file once, into a `FileModel`, and hands both
analyses what they need: the tokens to duplication, the units to
complexity. A gone file that cannot be read or parsed has no units, just
as it has no tokens today. A file generated by its header is skipped, as
it is today.

*Alternative:* a second pass over the per-file findings, which rewrites a
`cyclomatic-new` finding once a removed match turns up. It would need the
removed units anyway, and would split one rule's logic in two.

### D2. A moved unit is matched by its own name

First, as today, each file's after units are matched by qualified name.
What is left on both sides goes into one pool per family: the unmatched
after units of every changed file, and the unmatched before units of
every changed file together with every unit of a gone file. The pool is
grouped by *own name*, the last segment of the qualified name. The split
happens at the last `.` outside `()`, `<>` and `[]`, so that
`Cart.Total(System.Int32)` gives `Total(System.Int32)` and
`<Id as From<a::B>>.from` gives `from`. A `#2` suffix stays part of the
own name. In each group:

- one after unit and one removed unit: they are matched;
- otherwise, an after unit and a removed unit with the same fingerprint
  are matched when neither has another partner with that fingerprint in
  the group;
- the rest stay new or removed.

A matched pair is then judged like a pair matched by name.

The grouping is deterministic and does not depend on file order. A unit
can be matched at most once.

*Why own name:* SV19's method changed its modifiers (`private` to
`public`), so its fingerprint changed. A move very often comes with such
small edits. A fingerprint-only match would miss it.

*Why not more:* a heuristic that also matches renames would turn some
real new functions into increases. The spec's "Renamed function" stays.

### D3. A token records its unit; inlining is judged on tokens

`Token` gets `unit: Option<u32>`: the index, in `FileModel::functions`,
of the unit whose own code the token is, or `None` outside any unit.
`Tokens::push` takes it from the caller. Each adapter already has that
unit at hand where it hashes the same leaf into the fingerprint. Token
text does not change, so neither does duplication (it reads only
`text`), nor its tests.

A removed unit `R` is inlined into a unit `U` when all of these hold:

- `U` was matched (D2 or by name) and got more complex;
- `R` is still removed after D2, and is in the same family;
- `R` has decision points (complexity above 1);
- the longest common subsequence of `R`'s own tokens and `U`'s after own
  tokens is at least half as long as `R`'s own tokens.

The token texts are compared after interning them to integers. The
subsequence is computed with one row of dynamic programming, so it takes
O(|R|·|U|) time and O(|U|) memory.

Each `R` is credited to one `U`: the one whose subsequence covers the
largest share of `R`. Ties go to the first `U` by path, then by line.
`U`'s *credited before* is its before value plus the sum of
(complexity − 1) over the units credited to it. A finding is reported
only when the after value exceeds the credited before. Its severity
comes from that growth: 1 to 4 is a Warning, 5 or more an Error.

*Why half, in order:* an inlined body keeps its order but loses or gains
a few lines (CL11 renamed a log message, and removed V1 and the ternary
around both). Half rules out a function whose code merely resembles the
growth. Below half, a hidden real increase is a worse failure than one
more Warning. Checked on the evaluation pull requests in task 3.3.

*Why own tokens:* complexity is counted on own code, so the evidence
should be the same code. With an end line, nested named units would get
mixed in.

*Alternative:* credit every function removed from the same file, with no
evidence. It is simpler, but a pull request that deletes dead code and
adds logic elsewhere would go silent.

### D4. Messages and metric

- Moved: `<name>: cyclomatic complexity <before> -> <after> (+<delta>), moved from <old name>`.
  The old qualified name tells where the unit came from; its file is not
  in the message.
- Inlined: `(+<delta>, +<growth> beyond the inlined <names>)` in place
  of `(+<delta>)`, with the names in their order in the before version.
  A moved unit that also inlined code gets both forms.
- The metric keeps the real before and after values. `<delta>` is the
  real delta, and only the severity and `<growth>` use the credited
  before. Report formats that print the metric stay true.

### D5. Two pull requests

1. **PR 1:** D1, D2 and the moved-function messages, with fixtures and a
   CLI test that moves a method into a new file.
2. **PR 2:** D3 and the inlining message; the re-measurement of the 150
   pull requests; the README; the journal; the archive.

Each one stands alone. After PR 1, inlining is still reported as today.

## Risks / Trade-offs

- **Run time.** The pool is linear, and LCS only runs for pairs of a
  grown unit with a removed unit that has decision points. A big split
  pull request has many removed units but few grown ones. Mitigation: the
  re-measurement checks the 30-second budget on all 150 pull requests,
  and the three split pull requests in particular (server 8854, 8856,
  8859).
- **A hidden real increase.** If `U` grows by its own logic and also
  inlines `R`, the credit covers only `R`'s decision points, so the
  logic added beyond them is still reported. A function that both
  absorbs `R` and drops logic of its own could hide an increase of the
  same size. That is accepted: the code did not get more complex in
  total.
- **A wrong move match.** Two unrelated functions with the same own name,
  one removed and one added in the same change, are compared. The result
  is an increase finding, or none, where today a new-function finding
  would be. This needs a removed function and an unrelated new one of
  the same own name in one change, which is rare, and the finding says
  "moved from", so a reader can see it.
- **`Token` gains a field.** `Token` is a public type of `qgate-lang`,
  and code that builds it literally must add the field. The only users
  are in this workspace.

## Migration Plan

None. qgate stores nothing between runs; base and head are analyzed by
the same binary.
