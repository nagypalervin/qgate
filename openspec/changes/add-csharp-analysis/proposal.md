# Proposal: add-csharp-analysis

## Why

The partner teams write C# as well as TypeScript, and their pull requests
run in Azure Pipelines, where qgate now comments. For a `.cs` file qgate
reports nothing today: complexity and copied code in C# grow unseen. The
roadmap row "Languages" puts C# next, after M4.

## What Changes

- **A C# language adapter** in `qgate-lang` (tree-sitter-c-sharp): the
  same `FileModel` as for TypeScript (function units with their
  cyclomatic complexity, and normalized tokens), so the complexity and
  duplication analyzers work on C# unchanged.
- **C# files take part** in both modes: `.cs` in the two-file form and
  among the changed files of revision mode, including the working tree,
  the Claude Code hook and the MCP server, which run the same check.
- **Units and names:** methods, constructors, finalizers, operators,
  accessors and local functions are units; lambdas and anonymous methods
  count towards their named ancestor. A unit is named by its types and
  its own name, without the namespace, and a method-like unit carries its
  parameter types, so overloads keep their names when one is added or
  moved: `Cart.Total(int)`.
- **Decision points** for C#: `if`, the four loops, `case` labels and
  switch expression arms (not `default` or `_`), `when` guards and
  filters, `catch`, `?:`, `&&`, `||`, `??`, `??=`, `?.`, `?[]`, and the
  pattern combinators `and` and `or`.
- **Tokens for copies:** identifiers and literals become placeholders as
  in TypeScript; `using` directives, namespace declarations, preprocessor
  lines and comments produce none. Types are code in C# and keep their
  tokens.
- **Generated code is skipped,** by Roslyn's convention: file names such
  as `*.Designer.cs` and `*.g.cs`, or an `<auto-generated` comment at the
  top. EF Core's model snapshots and migration designers would otherwise
  report duplicates in every migration.
- **Copies are found within one language:** a C# block is compared with
  C# files only, a TypeScript block with TypeScript and JavaScript files.
- **The two-file form** rejects a C# file compared with a TypeScript one.
- **Version 0.4.0,** and the README says what qgate measures in C#.

### Out of scope

- **Architecture rules for C#.** `using` names namespaces, not files, so
  `from`/`to` path globs do not fit; it needs a design of its own. A
  `.cs` file has no architecture findings.
- **An exclude list in `qgate.toml`** for other unwanted files (for
  example the migrations themselves). If the evaluation below shows noise,
  it becomes its own change.
- **Other .NET languages** (VB.NET, F#), Razor (`.cshtml`, `.razor`) and
  C# script files (`.csx`).
- **Preprocessor evaluation:** qgate does not pick an `#if` branch.

### For Gate 1

Each question has a recommendation; design.md has the reasons.

1. **Overloads: parameter types in every method name** (`Cart.Total(int)`)
   instead of TypeScript's `#2` suffix by source order. With the suffix,
   adding an overload above another renames it, and qgate compares the
   wrong bodies. The price: changing a parameter's type makes the method
   "new", like a rename. *Recommended: parameter types.*
2. **Generated files: skip them silently** by Roslyn's convention, with no
   setting. *Recommended: yes.*
3. **The decision points above,** with two choices that differ from the
   TypeScript list: optional parameter values do not count (C# evaluates
   them at the call site, not in the method), and the pattern
   combinators `and` and `or` count like `&&` and `||`. *Recommended:
   as listed.*
4. **A file whose `#if` branches open blocks** cannot be parsed and gets
   the usual `input/unparsable` Warning. The evaluation measures how
   often that happens. *Recommended: accept for now.*
5. **Evaluation on real code before the release:** qgate on the recent
   history of two public C# repositories (by default `dotnet/eShop` and
   `jasontaylordev/CleanArchitecture`, or ones Ervin names), recording
   unparsable files, generated files, findings and run time. *Recommended:
   yes.*
6. **One Azure Pipelines run with a C# pull request** in the rehearsal
   project after the release, on a Windows agent. The integration does
   not change, but the partners' setup is exactly this. It needs a PAT
   that is valid on the day of the run (the current one expires on
   2026-11-17). *Recommended: yes.*

**Decided at Gate 1 (2026-11-13):** Ervin approved the proposal with
every recommendation, including the two default repositories for the
evaluation.

## Capabilities

### New Capabilities

- `csharp-analysis`: how qgate reads C#: which files, generated-code
  skipping, function units and their names, decision points, normalized
  tokens.

### Modified Capabilities

- `complexity-analysis`: "Cyclomatic complexity of a function" says that
  its TypeScript requirements apply to TypeScript, and `csharp-analysis`
  defines units and decision points for C#; matching, rules and findings
  apply to both.
- `duplication-analysis`: "Code without tokens" applies to TypeScript
  and JavaScript; "Compared files" compares files of the same language
  only.
- `revision-input`: "Only changed, supported files are analyzed" adds
  `.cs` and leaves generated C# files out.
- `check-command`: "Supported input files" adds `.cs` and rejects a C#
  file compared with a TypeScript one.

## Impact

- **Code:**
  - `crates/qgate-lang`: a `csharp` module and `Language::CSharp`;
  - `crates/qgate-cli`: extensions, generated files, the language of a
    duplication comparison;
  - fixture-based tests in `qgate-analyzers` and CLI tests.
- **Dependency:** `tree-sitter-c-sharp` (MIT, from the tree-sitter
  organization, no further dependencies than `tree-sitter-language`,
  which `tree-sitter-typescript` already brings). The spike parsed C# 12
  syntax with it under `tree-sitter` 0.26.
- **Binary size:** the grammar adds its parse tables to every release
  binary; the size goes into the release record.
- **Docs:** README sections on what qgate checks, and the roadmap row.
- **Release:** 0.4.0, including `action.yml`.
- **Three pull requests:** the adapter; the wiring, the evaluation and the
  version; then, after 0.4.0 is out, the Azure run, the release record,
  the journal entry and the archive.
